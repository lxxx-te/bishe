# 多源新闻事件的向量聚合与检索系统

> 毕业设计 · 设计与实现

设计与实现一个把多家媒体报道合并为"事件单元"、并在其上做可溯源问答与事件级输出的系统。研究目标不是算法创新，而是**做出一套可运行、可验证设计决策合理性的端到端系统**。算法与数据评测作为第 5 章"设计验证"，支撑设计决策的合理性。

---

## 系统解决什么问题

同一新闻事件被多家媒体报道，造成内容冗余、事实散落、查证困难：
- 同一事件，人民网/中新网/澎湃各发一篇，标题与措辞都不同
- 各家事实细节可能互补（时间、地点、数据互相补充）
- 用户在普通新闻 App 里只看到一篇就完，不会帮你对比各家说法

本系统把多家报道合并成一个"事件"，在其上做合并摘要、事件级输出（每日简报 / RSS 事件流）与可溯源问答。

## 为什么不是推荐系统

新闻推荐是今日头条 / 腾讯新闻主场（协同过滤 + 深度 CTR 预估 + 万级 A/B），自研玩具级 content-based 过滤落后十年且不可验证。本系统刻意**不在此轴竞争**，推荐降级为按兴趣标签过滤 + 全局热门兜底，不作为设计交付物。

差异化（头条不做的事）：

| 能力 | 头条 | 本系统 |
| :--- | :--- | :--- |
| 同一事件多源报道合并为一个事件 | 否 | 是 |
| 事件级输出（每日简报 / RSS 事件流） | 否 | 是 |
| 事件级 RAG + 引用溯源 | 否 | 是 |
| 个性化推荐 | 是 | 否（显式兴趣标签过滤） |

## 系统总体设计（按数据流向自顶向下分五层）

### 1. 数据采集层

定时抓取人民网、中国新闻网、澎湃新闻（经自部署 RSSHub 转 RSS）多家来源。澎湃作为不同性质源补充——官方媒体常互相转通讯社通稿，加入澎湃扩大覆盖与事件生命周期。每篇报道按网址去重入库，存进数据库"报道表"，包含标题、原文、发布时间、来源、摘要、向量等字段。

### 2. 数据处理层（两个子模块）

#### 2.1 摘要与向量化模块

每篇报道原文太长，用 DeepSeek 生成 100 字事实摘要，并自动检查摘要里有没有抄原文连续 15 个字以上的片段，有就重写一遍（N-gram 校验）。然后把摘要转成一个 512 个数字组成的向量（可以理解为"内容的坐标"），方便后面比对内容相似度。摘要调一次缓存下来，不重复花钱；向量用本地 BGE-small-zh 模型算，零 API 成本。

#### 2.2 事件聚合模块（设计核心之一）

判断"两篇报道是不是讲同一件事"不能光看网址（不同源网址不同）也不能光看标题（同事件标题措辞不同）。设计了两道关：

- **关键词闸门**：两篇至少 1 个关键词重叠（比如都讲"火灾""某地"）才进入下一步
- **语义向量 ANN**：相似度 > 0.90 才判为同一事件

两关都过才算同一事件，合并成一个"事件"，各家报道挂在其下。阈值通过 100 对人工盲标 gold 集数据驱动标定：扫 0.50–0.95 画 P/R/F1 曲线，按"错并比漏并代价高十倍"原则选 **precision ≥ 0.9** 的点 = **0.90**（precision 0.929 / recall 1.000 / F1 0.963）。初版魔数 0.75 实测精度仅 0.134（86% false-merge），阈值不拍脑袋。

挂载新报道后，后台异步重算整个事件的合并摘要与向量中心（多源合并摘要 + 重 embed），避免首篇报道的措辞风格偏置了整个事件的代表向量，也让跨源细节互补进事件摘要。

### 3. 检索问答层

用户用一句自然语言提问，比如"最近三天关于新能源车的重大新闻"。系统走三段管道找答案：

| 段 | 做什么 | 为什么要这一段 |
| :--- | :--- | :--- |
| ① 时间预过滤 | SQL 按时间范围砍掉过期事件 | 向量不认时间，必须先 SQL 过滤堵这个洞 |
| ② 向量召回 Top-20 | pgvector ANN 粗召回最像的 20 个事件 | 召回导向，宁滥勿缺 |
| ③ reranker 精排 Top-5 | bge-reranker（更准但更慢的 cross-encoder 模型）打分精排 | 提 precision，砍掉向量召回里混进的相关度差事件 |

→ DeepSeek 在受约束 prompt 下流式生成答案：

- **强制引用**：每一句必须带 `[事件#X]` 引用，点进去能看到这个事件的全部原始报道
- **不足拒答**：库里信息不足时主动说"信息不足"，不硬编（防幻觉靠结构性保证，不靠事后让 LLM 自己查自己）
- **整句缓冲**：流式输出按整句缓冲后再推前端，保证每句末尾的引用不会因为字符流而丢失
- **SSE 推流**：后端用 Server-Sent Events 流式推送，前端逐句渐次出现

前端按用户勾选的兴趣标签预过滤事件流，不做行为画像，规避个保法。

### 4. 输出层（每日简报 + RSS 事件流）

事件级聚合的成果以两种结构化形式对外输出，逐字段可追溯、零新增 LLM 调用：

- **每日简报** `GET /api/digest?date=YYYY-MM-DD`：选稿规则 = **按多源度排序**（覆盖事件的不同媒体来源数，多源事件排前面）取 Top-10。每条含标题（首篇报道标题）、合并摘要、分类、来源清单、原文链接。
- **RSS 事件流** `GET /feed/events.rss?days=N&category=X`：标准 RSS 2.0 订阅源，一条 = 一个事件，item link 指向首篇报道原文，description 为合并摘要 + 全部来源 + 关键词标签。可在任意阅读器订阅。

### 5. 前端展示层

Vue 3 + Vite 实现四个页面：

- **onboarding 兴趣标签页**（首次进入选 2-3 个标签，存进 `user_profile` 表，不做行为追踪）
- **事件流卡片列表**（每张卡显示这个事件的合并摘要、分类、关键词、多源列表，默认按多源度排）
- **每日简报页**（日期选择 + 多源优先清单 + RSS 订阅入口）
- **RAG 对话框**（SSE 解析、整句渲染、引用可点击溯源到事件卡、原文链接可跳转原媒体页面）

#### 事件卡长什么样（举例）

```
┌────────────────────────────────────────────┐
│ 政治   6月3日                      🔥 4源   │  多源度=几家媒体报道
├────────────────────────────────────────────┤
│ [合并摘要] 国务院总理李强签署《政务数据     │  LLM 多源合并摘要
│  共享条例》，自2025年8月1日起施行……        │
├────────────────────────────────────────────┤
│ #政务数据共享条例 #政务大数据体系 #国务院   │  关键词闸门累积集
├────────────────────────────────────────────┤
│ [多源列表]                                  │
│  · 人民网  "公布《政务数据共享条例》" →原文 │  一行一篇报道
│  · 中新网  "……"                    →原文   │  可点跳转原文
└────────────────────────────────────────────┘
```

三个区分别对应数据库里一个事件存的不同字段：摘要区是 `merged_summary`（多源 LLM 合并）；关键词区是 `keywords`（挂载时累积扩集）；多源列表是事件下挂载的全部 `news_report`。

## 数据库设计

6 张表，两层结构（1 事件 : N 报道）：

- `news_report` — 报道表：source_site, title, **raw_text（全文，抓了不删，允许 NULL——RSS 抽到空 content 的项也存 title+link）**, original_url, publish_time, summary（LLM 缓存）, embedding, event_id（FK）, is_paid
- `news_event` — 事件表：merged_summary（多源 LLM 合并摘要）, embedding, **keywords**（ARRAY Text，GIN 索引支持数组相交查询）, source_count（报道篇数计数，仅内部维护；**对外展示/排序口径 = 多源度**，即 COUNT(DISTINCT source_site)，API 字段 `source_breadth`）, **event_publish_time**（= MIN over reports.publish_time，写入时算，P5 时间预过滤的索引列）, category, ts
- `user_profile` — 用户兴趣表：user_id, interest_tags（JSONB）, consent_at（仅显式偏好，onboarding 一次授权）
- `rag_eval_set` / `rag_eval_run` — RAG 评测表
- `dedup_eval_set` — 去重调参表

> **不设 `user_read_history`**：不做行为画像，规避个人信息合规风险（设计决策）。

用 PostgreSQL + pgvector 插件在一个库里同时存关系数据和向量数据，避免引入 Milvus 增加运维负担。keywords 字段用 GIN 索引支持 PostgreSQL 数组相交查询（关键词闸门那一步用得到）。数据库迁移开发期采用**reset 策略**（DROP+CREATE+init_schema，5 秒搞定，scripts/reset_db.sh 一键），不引 alembic——毕设期 schema 变动次数少，alembic 学习成本不值；论文写"开发期 reset、生产部署引 alembic"即可。

## 第 5 章 系统测试与设计验证

两套独立人工标注集，**不是研究贡献**，是支撑设计决策合理性的验证手段。两套都基于答辩前一周的数据库快照构造，保证可复现（快照库：`news_aggregator_eval`，由 pg_dump 冻结）。

### 5.1 去重阈值选取实验

从库里随机抽 200 篇，每篇取"语义最像的 3 个邻居"配成对（专挑难判对的样本），去重到 ~500 对后随机抽 100 对，人工盲标每对是不是同一事件。扫不同阈值 0.50–0.95，每个阈值下算系统判别和人工标签的 precision、recall、F1，画曲线。按"错并比漏并代价高十倍"原则选 **precision ≥ 0.9** 的阈值 = **0.90**（precision 0.929 / recall 1.000 / F1 0.963）——证明阈值是数据驱动不是拍脑袋。

### 5.2 RAG 管道消融实验

手写 50 个问题并标注正确答案事件（按 IR 文献标准定义的 set recall@5 标完整 gold 事件集），跑系统看每段管道加上去的效果（48 条有效样本，冻结快照库实测）：

| 配置 | recall@5 | faithfulness |
| :--- | :--- | :--- |
| ① 最朴素：向量召回 Top-5（无时间过滤、无 reranker、无受约束生成） | 0.353 | 0.947 |
| ② ① + 时间预过滤 | 0.389 | 0.933 |
| ③ ② + reranker 重排 | 0.434 | 0.943 |
| ④ ③ + 受约束生成（小样本） | 0.434 | 1.000 |
| ⑤ 最终版（全量 48 条） | 0.452 | 0.941 |

每一行都证明一段管道有贡献：去掉时间预过滤 recall@5 掉一截；去掉 reranker 掉一截；去掉受约束生成 faithfulness 掉一截。一张消融对比表比一万字解释硬。

### 5.3 防幻觉策略：保证 vs 指标拆分

- **保证（结构性）**：强制每句带事件引用 + 受约束生成（"只能用 context，否则说信息不足"）+ 用户可点击溯源 + 整句缓冲后渲染保证引用必带。防幻觉靠事前结构拦截，不靠事后 LLM 自查。
- **指标（公开标注）**：faithfulness 用 RAGAS LLM-as-judge，明确标注为"LLM 评估指标，非硬保证"；附带拒答率作为更硬信号（拒答率高 = 检索失败而非系统稳重）。

## 技术选型

| 层 | 选型 | 理由 |
| :--- | :--- | :--- |
| 后端 | Python + FastAPI | ML / 评测生态全在 Python |
| 数据库 | PostgreSQL + pgvector（源码编译） | 关系 + 向量一库搞定，不增 Milvus 运维 |
| embedding / 重排 | BGE-small-zh + bge-reranker-base（本地 CPU 推理） | 零 API 成本、评测可复现（模型权重不漂移） |
| LLM | DeepSeek | 摘要一次性缓存；RAG 受约束生成；SSE 流式；200/日上限控量 |
| 前端 | Vue 3 + Vite + SSE | 流式输出体验 |
| 转 RSS | 自部署 RSSHub（Docker，:1200） | 澎湃等无 RSS 源统一转 RSS |

## 数据源与合规

- **官方 RSS** — 人民网、中国新闻网。发布方主动提供，使用 RSS 协议，合规性最干净。
- **NewsAPI.org** — 商业 API，条款允许个人 / 教育用途（国际新闻补充）。
- **澎湃新闻** — 经自部署 RSSHub 抓取代理获取，**非发布方主动授权**，仅作源覆盖补充（论文合规段如实标注）。
- **抓全文入库不删**：`news_report.raw_text` 存全文用于摘要生成研究。
- **原文链接可点击跳转**原媒体页面；系统不在端内复制或缓存全文内容给用户。
- **不做行为画像** → 无 `user_read_history` → 个保法暴露最小化。

**论文合规段**：
> 本系统为毕业设计研究原型，不公开部署、不向公众提供访问，仅在受控环境内用于设计验证。系统存储原文用于摘要生成研究，摘要为大模型生成的抽象式事实复述，并经 N-gram 校验避免复现原文连续片段。原文链接以导航形式提供跳转，不构成对全文的复制或传播。数据源中 RSSHub 为社区抓取代理非发布方授权，特此标注。

## 当前系统实测状态

### 数据规模

- 200 篇报道（人民网 100 / 中国新闻网 60 / 澎湃新闻 20 / 澎湃热榜 20）
- 176 个事件（15 个多源合并事件，最大 4 源聚合）
- 跨源聚合实例：澎湃 × 中国新闻网 × 澎湃热榜三方聚合事件已产生

### 评测结果（48 条，冻结快照库 `news_aggregator_eval`）

| 指标 | 结果 |
| :--- | :--- |
| avg recall@5 | 0.452 |
| refusal accuracy | 0.958 |
| citation valid rate | 1.000 |
| avg faithfulness | 0.941 |

> 注：faithfulness 0.978→0.941 为移除事实槽位模块（5W1H + 冲突分级）后的实测值。该模块移除后系统简化、context 构造变化，检索类指标持平，faithfulness 略降但仍在 0.94 高位——设计决策"删事实互证、保留摘要与事件级聚合"的代价已如实记录。
