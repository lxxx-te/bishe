def has_complete_text(text: str) -> bool:
    t = text.rstrip()
    while t and t.endswith(_CLOSING_WRAPPERS):   # 「他说："……。"」 引语结尾合法

二 · A线核心：dedup_one 的三岔口app/services/dedup.py:112

每篇新报道面对三个出口：跳过 / attach 进旧事件 / spawn 成新事件。

async def dedup_one(session, report, keywords) -> dict:
    if report.embedding is None:                        # ① 无向量 → 无法语义去重
        return {"action": "skipped_null_embedding"}
    candidates = await _find_candidate_events(session, keywords)
    if not candidates:                                  # ② 关键词零重叠 → 直接 spawn
        event = await _spawn_event(session, report, keywords)
        return {"action": "spawn", ...}
    best_event, best_sim = None, 0.0
    for ev in candidates:                               # ③ 小候选集上纯 Python 余弦
        sim = _cosine(report.embedding, ev.embedding)
        if sim > best_sim: best_sim, best_event = sim, ev
    if best_event and best_sim > DEDUP_THRESHOLD:       ← 0.90，严格大于
        await _attach_to_event(session, report, best_event, keywords)
        return {"action": "attach", ...}
    return {"action": "spawn", ...}                    # ④ 有候选但都不够像 → spawn

两级漏斗的设计意图

层函数机制为什么
第一级 关键词闸门_find_candidate_eventsSQL keywords && :kws（数组重叠运算符），GIN 索引，最多取 50 个候选把全表 ANN 变成小集合精算；关键词不重叠的事件基本不可能同事件
第二级 向量兜底_cosine 循环候选 ≤50 个，纯 Python 点积即可；阈值 > 0.90 才 attach向量相似但关键词措辞不同的场景由它接住——两级互为安全边际
陷阱提醒（答辩可能被问）：本文件顶部 docstring 写着「max similarity > 0.75」——注释在撒谎，代码真相是 DEDUP_THRESHOLD = settings.dedup_sim_threshold（默认 0.90）。读代码永远以代码为准。另外历史教训：0.75 时 precision 只有 0.134，灾难级。

attach 之后发生什么（Q2 fix + Q20 fix）

async def _attach_to_event(session, report, event, new_keywords):
    report.event_id = event.id
    event.source_count += 1                          # 内部计数列：数的是报道篇数
    merged = list(set((event.keywords or []) + new_keywords))[:6]   ← 并集去重，封顶6个
    event.keywords = merged
    if report.publish_time and report.publish_time < event.event_publish_time:
        event.event_publish_time = report.publish_time    ← 取 MIN，供时间预过滤
    await session.commit()
    # 随后 BackgroundTasks 异步调 P4：LLM 重合并所有报告摘要 → 重 embed 事件中心
  • keywords 并集封顶 6 个（Q2 fix）：否则首篇的关键词固化，后续措辞不同的报道撞不上闸门，会错误 spawn 出重复事件（lessons/0002 讲过的 bug）。
  • event_publish_time 取 MIN：事件时间=最早报道时间，这是 B 线时间预过滤的索引列。
  • P4 异步重算（Q20 fix）：事件向量不再停留在首篇「锚点」，而是所有成员摘要的 LLM 合并结果的 embedding——防单篇措辞偏置。
  • source_count 是内部计数：对外展示口径是 source_breadth = COUNT(DISTINCT source_site)，API 字段已改名。此列保留是为了不破坏历史评测可复现性。

async def rag_answer_stream(session, query_text, ...):
    event_ids = await retrieve(session, query_text, ...)      # ← 三段检索，见下节
    yield f"event: meta\ndata: {json.dumps({'event_ids': event_ids})}\n\n"
    if not event_ids:                                          ← 检索为空 = 硬拒答
        yield "event: token\ndata: 信息不足\n\n"
        yield 'event: done\ndata: {"refusal": true}\n\n'; return
    events_with_reports = await fetch_events_with_reports(session, event_ids)
    context = _build_context(events_with_reports)              # 每事件一块：摘要/类别/时间/来源
    stream = await client.chat.completions.create(model=..., stream=True,
                 messages=[{"role":"system", "content": RAG_SYSTEM},      ← 受约束 prompt
                           {"role":"user",   "content": user_prompt}], ...)
    buf = ""
    async for chunk in stream:
        buf += delta; full_text += delta
        while (m := _SENT_BOUNDARY.search(buf)):               ← 攒到句号才发
            sentence, buf = buf[:m.end()].strip(), buf[m.end():]
            yield _sse_token(sentence)
    cited_ids = _CITATION_RE.findall(full_text)                # \[事件#(\d+)\]
    valid = [c for c in cited_ids if c in event_ids]          ← 引用必须∈召回集
    yield f'event: done\ndata: {{"refusal": ..., "citations_valid": ...}}'
为什么按句缓冲而不是逐 token？（Q21 裁决）强制引用 [事件#51] 若在 token 中间被切断，前端会渲染出半个括号。攒到 。！？\n 再整句 flush，保证引用完整。citations_valid 定义：LLM 引用的事件 ID 必须全部 ∈ 本次召回归还的 event_ids——这是「受约束生成降幻觉」指标 citation_valid_rate=1.000 的计算处。

四 · B线心脏：retrieve 三段漏斗app/services/rag/retrieval.py:216

_parse_time_window中文时间词→区间→ stage1_time_filterSQL btree，≤200 候选→ stage2_ann_recall<=> cosine Top-20→ stage3_rerankbge cross-encoder Top-5
段关键代码事实设计理由
Stage 1 时间预过滤_parse_time_window 用 datetime.now() 解析「最近一周」等；无时间词则完全不过滤，仅按 source_count 排序取前 200embedding 天生不认识时间，必须 SQL 补刀。⚠️ now() 正是「冻结快照库答不出最近一周」误拒案的案发现场
Stage 2 ANN 召回原生 SQL ORDER BY embedding <=> :q LIMIT 20，查询向量拼成字符串 "[0.1,0.2,...]" 传入asyncpg 需要 string cast；HNSW 索引在此生效。20 = 召回导向，宁滥勿缺
Stage 3 精排CrossEncoder 在 asyncio.to_thread 里跑（模型是同步的）；失败时降级 score = 1 - distance 沿用 ANN 序query 和文档拼在一起过 cross-encoder，精度远高于各自编码；单例加载避免每次请求载模型
消融开关就在这：use_time_filter / use_reranker / use_constrained_generation 三个布尔参数即 run_ablation.py 五行配置的操作对象——砍一段重跑评测，掉分即证该段贡献（0.353 → 0.452）。

五 · 三问自测quiz

Q1. 一篇报道 embedding 非 NULL、关键词与某事件重叠、但最高余弦只有 0.88。它的结局？

spawn 新事件。阈值是严格大于 0.90（best_sim > DEDUP_THRESHOLD）。注意此时它不会因为关键词重叠就 attach——闸门只筛候选，不做决定。0.88 落在灰区正是两级设计的缓冲带。

Q2. 用户问「最近一周政治新闻」，冻结快照库里最新数据是 14 个月前的。retrieve 会返回什么？为什么？

空列表 → rag_answer_stream 直接硬拒答（meta 空 → token「信息不足」→ done refusal:true）。根因链：_parse_time_window 用墙钟 datetime.now() 减 7 天 → 快照库没有任何事件落在窗口内 → stage1 返回 []。这就是评测里 46/48=0.958 那 2 分扣分处，与拒答判别逻辑无关。

Q3. LLM 答案里写了 [事件#99]，但本次 meta 给的是 [51,63,76]。done 事件的 citations_valid 是？

false。valid = [c for c in cited_ids if c in event_ids] → #99 ∉ 召回集。citation_valid_rate=1.000 表示历次评测从未出现这种越界引用——这正是受约束生成要证明的东西。
