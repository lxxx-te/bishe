BISHE TEACH · LESSON 05

Schema 与索引：每个列和索引都有理由

上一课讲了函数怎么跑。这一课往下一层：表为什么长这样、索引为什么是这四种——核心只有一句话：索引为查询形状服务。所有内容来自 models.py 与真实库的 pg_indexes，无一处凭记忆。

① 六张表的全景：两张主表 + 四张配角表

news_report ──N:1──▶ news_event          ◀── 核心两表（业务全在这）
     │                    │
     └─1:N─▶ news_report_fact   news_event ──▶ fact_slots / conflict_flags (JSONB 内嵌)

user_profile          rag_eval_set → rag_eval_run          dedup_eval_set
（显式兴趣标签）        （RAG 评测：题集 + 每次运行快照）        （去重阈值调优金标）

读法：news_report.event_id 外键指向 news_event.id，一篇报道最多属于一个事件；事件删了报道不删（下面讲为什么）。四张配角表全部服务于「可评测、可复现」——这是本毕设和其他新闻聚合项目拉开差距的地方。

② news_report：六列有故事的列

列定义为什么
original_urlString(1024) UNIQUEP1 URL 去重的最后防线。应用层查重失败（并发、崩溃）数据库也会拒绝重复插入——唯一约束是免费的幂等保险丝。
raw_textText 可 NULL历史遗留允许 NULL（准入闸门上线前的旧数据）；新代码里残句在 persist 就被拒收。
embeddingVector(512) 可 NULLNULL 当业务过滤器用：raw_text 为空的行不造假向量（Q2 fix），NULL 自动把该行排除出 P3 ANN 去重和 P5 检索——不用额外的布尔列。
summary_source'llm' / 'fallback'Q1 fix：P2 重处理时只挑 != 'llm' 的行补摘要——断点续跑，LLM 挂了不重烧已成功的行。
summary_model
summary_tokens		逐行记录Q15 fix：每行存用了哪个模型版本、烧了多少 token。论文可复现性声明和成本审计的数据来源。
event_idFK，ondelete=SET NULL删事件时报道保留、指针清空。event_id IS NULL 恰好就是 P3 的扫描条件——「待重新聚合」不需要额外状态列。
设计原则一：NULL 当语义过滤器 embedding 为 NULL ≠ 数据缺失，而是「此行不具备向量资格」。省掉 needs_embedding 布尔列，SQL 里 embedding IS NOT NULL 一刀切干净。

③ news_event：五列有故事的列

列定义为什么
event_publish_time写时预计算 = MIN(报道时间)反规范化换速度：P5 时间预过滤要按时间范围扫事件，有了这列直接走 btree 索引，不必每次 JOIN 报道表再 GROUP BY 取 MIN。
keywordsARRAY(Text) + GIN关键词闸门的 SQL 是 keywords && ARRAY['…']（数组相交）。数组相交只有 GIN 能服务，btree 对它无意义。
source_countInteger 内部计数器attach 时 +1 的报道篇数。对外展示口径是 COUNT(DISTINCT source_site)=source_breadth（API 字段 source_breadth）。列保留是为了历史评测数字可复现。
fact_slots / conflict_flagsJSONB5W1H 槽位是半结构化数据，结构还在演进（v5）——JSONB 免 ALTER TABLE。GIN 索引支持「查有冲突的事件」。
merged_summary + embeddingText + Vector(512)事件级 LLM 合并摘要再 embed（P4 异步重算）：事件向量中心由全体报道共同决定，不被首篇措辞偏置。
反规范化的代价要诚实 MIN(publish_time) 写时算意味着每次 attach 都要多一条 UPDATE 维护它。这笔交易划算是因为读写比悬殊（读几百次才写一次）。如果反过来写多读少，就该现算。

④ 四种索引，各自服务一种查询形状

真实库里的索引（pg_indexes 输出），每一个都对应一条真实 SQL：

索引DDL服务的查询
HNSW 向量USING hnsw (embedding vector_cosine_ops) WITH (m='16', ef_construction='64')P3 去重与 P5 召回的 embedding <=> :query 余弦近邻
GIN 数组USING gin (keywords)关键词闸门 keywords && ARRAY[...]
btree 时间USING btree (event_publish_time)P5 预过滤 >= x AND < y 范围扫描；列表页时间排序
唯一 btreeUNIQUE (original_url)P1 幂等插入 + URL 点查

其余 btree（category、source_count、ts、publish_time、source_site、event_id）同理：外键索引用于 JOIN/级联，低基数列索引服务于过滤下拉框。没有一条索引是「以防万一」加上去的。

HNSW 两个参数在赌什么

HNSW = 分层可导航小世界图，把暴力 O(N) 扫描变成近似 O(logN) 跳转。两个旋钮：

  • m=16 —— 每个节点的出边数。边越多图越连通、召回越高，内存和构建时间也涨。16 是 pgvector 的常用值。
  • ef_construction=64 —— 建图时候选队列深度，决定图的质量上限。查询侧另有 ef_search（本项目用 pgvector 默认值，未调——论文如实标注）。
答辩弹药：为什么 HNSW 不用 IVFFlat IVFFlat 要先聚类出中心点（训练步骤），数据量小的时候划分不稳、召回波动大；HNSW 免训练、增量插入友好、中小数据集表现稳定。187 个事件的库用 HNSW 是量体裁衣，不是追时髦。

⑤ 把这一课压缩成四条原则

原则一先写 SQL，再定索引。索引为查询形状服务，「以后可能查」不是加索引的理由。
原则二NULL 可以承载业务语义（不合格即无向量），但要用得像 embedding 这样有明确判据。
原则三读多写少的聚合值（MIN 时间、计数器）写时预计算，把 JOIN 成本从每次读移到一次写。
原则四数据库约束是最后防线：UNIQUE 管幂等，FK ondelete 管级联语义，应用层代码只是第一道关。

⑥ 三问自测

问1：为什么 keywords 用 GIN 而 event_publish_time 用 btree？互换行不行？
答案

不行。GIN 是倒排结构，服务「集合包含」类谓词（&&）；btree 有序，服务范围与排序（>=、ORDER BY）。数组相交给 btree 它不知道怎么比大小；范围扫描给 GIN 是杀鸡用牛刀且不支持。

问2：删掉一个事件后，它的报道去哪了？P3 会怎么处理它们？
答案

报道还在，event_id 被 SET NULL。P3 扫描条件正是 event_id IS NULL，所以它们会被重新提取关键词、重新走闸门+向量判定——要么挂进别的现存事件，要么 spawn 成新事件。删除操作天然触发了「重新聚合」。

问3：event_publish_time 为什么不在查询时 SUM/MIN 现算？什么情况下这个决定会变成错误？
答案

现算要 JOIN news_report GROUP BY，时间预过滤就没法只用事件表的 btree 索引了。若系统变成「事件频繁变动」（每秒 attach 几十次）而读取很少，维护反规范化列的开销超过收益，那时该改回视图或现算。决策依据永远是读写比。
